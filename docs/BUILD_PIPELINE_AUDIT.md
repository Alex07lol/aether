# Production build and runtime audit

> **Status: the migration this audit argued for is DONE.** The build is now real ForgeGradle 2.1
> + MixinGradle 0.6 + embedded Mixin 0.7.11 (see `build.gradle` for the full decision record).
> Sections 1-7 below describe the pre-migration build and the hand-written remapper it once
> shipped; that remapper, the 89 compile stubs and the mapping-supply environment variables were
> deleted once the ForgeGradle pipeline was proven end to end (`runClient` with all five mixins
> applying, `reobfJar` verified by `scripts/verify.sh`). The text is kept as the record of *why*.

Aether's rendering problems are not, at bottom, rendering problems. They are build problems that
surface as rendering problems. This document records what the shipped artifact actually contains,
why it is not the artifact a Forge 1.8.9 mod needs to be, and what was changed so that it can be.

Everything below is measured from the artifact - compiled class files, the assembled jar and the
actual sources - rather than inferred from the source, because the source and the artifact disagreed
in exactly the way that matters.

---

## 0. Method

| Evidence | How it was produced |
| --- | --- |
| Every Minecraft member reference in Aether's compiled classes | `javap -p -c` over all 94 adapter classes, extracting `// Method` and `// Field` entries from the constant pool |
| Per-class attribution | the same, one class at a time, so a reference can be traced to the class that makes it |
| The shipped jar | assembled the way `forge189Jar` does (main + adapter classes + `src/forge189/resources`, `MixinConfigs` manifest) and listed entry by entry |
| Bytecode *inside the jar* | `javap` against the staged jar contents, not against the build tree |
| The remap step | run over the real 260-class build, with an empty mapping file (report mode) and with a complete one |
| Leaf's pipeline | its `build.gradle` and mixin configuration, read directly |

The audit found no way to launch Forge 1.8.9 in this environment (no Gradle distribution, no
mappings, no game jar, no launcher), so every claim here is about the artifact and its inputs. What
cannot be verified without a running client is called out as such in §12.

## 2. What the artifact actually contains

The adapter is compiled with `javac` against stubs whose member names are the development (MCP)
names: `drawScreen`, `pos`, `endVertex`, `getGlTextureId`, `fontRendererObj`. Nothing in the build
renames them. So they are what the jar ships.

From the assembled jar, `GlyphPageFontRenderer` alone:

```
// Method net/minecraft/client/renderer/Tessellator.draw
// Method net/minecraft/client/renderer/Tessellator.getInstance
// Method net/minecraft/client/renderer/Tessellator.getWorldRenderer
// Method net/minecraft/client/renderer/WorldRenderer.begin
// Method net/minecraft/client/renderer/WorldRenderer.color
// Method net/minecraft/client/renderer/WorldRenderer.endVertex
// Method net/minecraft/client/renderer/WorldRenderer.pos
```

A production Minecraft 1.8.9 runtime has none of those names. It has `func_78381_a`,
`func_181662_b`, `func_181675_d` and so on; FML's runtime remapper translates SRG names into the
runtime's, and it has never heard of MCP names. This is the same failure that produces the classic
1.8.9 development-jar error `NoSuchMethodError: ... getMinecraft().fontRendererObj`.

Across the whole adapter the artifact makes **100 call sites** into **48 distinct Minecraft members**
in development form:

| Area | Examples | Consequence on a production runtime |
| --- | --- | --- |
| All UI drawing | `Tessellator.draw/getInstance/getWorldRenderer`, `WorldRenderer.begin/pos/tex/color/endVertex`, `DefaultVertexFormats.POSITION*` | `NoSuchMethodError` on the first drawn primitive |
| The custom font | the above, plus `DynamicTexture.getGlTextureId/updateDynamicTexture` | `NoSuchMethodError` on the first text draw |
| Screen lifecycle | `GuiScreen.initGui` | `NoSuchMethodError` when the screen opens |
| HUD | `ItemStack.*`, `Potion.*`, `PotionEffect.*`, `StatCollector.translateToLocal`, `Block.*`, `WorldClient.getBlockState` | the ARMOR/POTION/BLOCK-INFO/ITEM elements throw |
| World drawing | `AxisAlignedBB.minX..maxZ/expand/offset`, `Material.air`, `MovingObjectPosition$MovingObjectType.BLOCK` | the selection box and waypoint paths throw |
| Mixins | `ItemCameraTransforms$TransformType.*`, `ItemStack.getItem` | remapped only by a refmap, which is not in the jar |

Beside that, the screens were already half-defended by hand. Every Aether screen carries a pair of
declarations per lifecycle hook - the development name and, written literally in the source, the SRG
delegate:

```java
public void initGui()                      { ... }   // development name
public void func_73866_w_()                { initGui(); }   // runtime name
```

`AetherQuickNavScreen` lines 42-262, and the same shape in all nine screens. On an obfuscated
runtime Minecraft dispatches `func_73866_w_`, which forwards to the development body, so the screens
are *not* inert there. This is the same hand-rolled reobfuscation the reflection layer performs,
applied to the one thing reflection cannot reach - and it is what makes the shipped jar's behaviour
so confusing: input and clicks work, text is missing, HUD elements crash, and nothing points at the
build.

## 3. Is the reflection layer compensating for a missing build step?

Yes, and that is exactly what it is. `Mc189Compat` looks each member up by its development name and
then by its SRG name at run time (`{"drawRect", "func_73734_a"}`), caches the `Method` and invokes it.
For the UI primitives this *works* on both runtimes, which is why the deck chrome can draw even
though the jar is not remapped. It is a hand-rolled reobfuscation, one call site at a time.

It is also incomplete, and its incompleteness has a shape: the paths that were converted work, and
the paths that were not are the ones that break. That is why the symptom set is so confusing - panels
draw, text does not, the HUD elements crash, and every screen is inert.

Three further costs come with the approach:

* It cannot fix a **declaration**. `drawScreen` is not a call to be reflected; it is a method
  Minecraft has to find. Only remapping renames it.
* It cannot fix an **inherited override** either, for the same reason.
* It pays `Method.invoke` per call site. The glyph path alone would become a reflective call per
  vertex if the drawing API were converted this way, which is why converting the remaining 100 sites
  to reflection is the wrong fix: the right one is to rename them.

## 4. Mixin

* `mixins.aether.json` declares `refmap: mixins.aether.refmap.json`, and no such file is in the jar:
  refmap generation is gated on `-PaetherSrgMappings` (plus a development Forge jar), and neither is
  present in a normal build. The declared refmap therefore never exists.
* Without a refmap, every `@Inject(method = "getFOVModifier", ...)` target stays a development name.
  Mixin resolves targets in the *runtime's* namespace, so nothing matches.
* There is no Mixin runtime in the jar and no way to start one: no `MixinBootstrap`, no `TweakClass`,
  no embedded `org.spongepowered` classes, and the 21 `org.spongepowered.asm` imports in the mixin
  classes resolve to nothing at run time. A `MixinConfigs` manifest attribute only means something to
  a Mixin runtime that is already present; Forge 1.8.9 does not provide the 0.7 API these mixins are
  written against, which is precisely why Leaf embeds Mixin 0.7.11 and points `TweakClass` at a
  tweaker that calls `MixinBootstrap.init()`.
* The configuration is defensive (`required: false`, `defaultRequire: 0`), so on a runtime where
  Mixin *is* present the injectors degrade to no-ops and log instead of crashing the client.

The net effect on production is the same either way: **the five mixins do not apply**. Zoom's FOV
override, the visual time/weather overrides, the freelook rotation freeze, the 1.7 item poses and the
hurt-camera scaling are all absent on a real client. That is a feature gap, not a crash, and it is
the one finding here that Aether cannot fix in its own code alone: either the artifact embeds and
bootstraps Mixin (Leaf's route), or those five behaviours need non-mixin implementations (mixin-free
alternatives exist for some of them, since the event bus already covers parts of the same ground).

## 5. Why `GlyphPageFontRenderer` appears in the logs

Because it is the active text renderer, not a leftover. The artifact is not ambiguous about this:

* `AetherClickGuiScreen` (line 318), `AetherMainMenuScreen` (line 70) and `AetherQuickNavScreen`
  (line 58) each take `fontManager.uiFont()` and pass it as the font to every text call;
* `AetherUi.textSmooth`, `AetherUi.stringWidth`, `Mc189Compat.drawString*` and `Mc189Compat.stringWidth`
  all dispatch to `GlyphPageFontRenderer` when the font they are handed is one;
* every Control Center page (`ModulesPage`, `ProfilesPage`, `ThemesPage`, `CosmeticsPage`,
  `SettingsPage`, `ScreenshotsPage`) and `ControlCenterRenderer` does the same.

So there is no discrepancy to reconcile: the custom font is the primary path, and the Minecraft
`FontRenderer` is the fallback only when the atlas has no texture at all. The earlier reading - "the
UI uses Minecraft's font renderer, so why is GlyphPage in the log" - came from the fallback branch in
`Mc189Compat.drawString`, and from the in-game font diagnostic, which prints the atlas size, the
texture id and where that id came from. The log line that mentions `getGlTextureId(): returned 0`
originates in the headless self-test, where the stub `DynamicTexture` genuinely cannot answer; it is
not evidence about a running client, and it should not be read as such.

## 6. Do the 89 stubs mask production failures?

They do not merely mask them - they *are* the reason the failures were invisible until the jar ran.
The stubs declare methods and fields that exist only in Aether's build tree:

| Stub member | Reality |
| --- | --- |
| `DynamicTexture.getGlTextureId()` returning 0 | the stub cannot answer; the real class has `func_110552_b` |
| `WorldRenderer.Batch`, `Tessellator.setRecording/resetRecorder/recordedDraws`, `GlStateManager.lastColor/resetLastColor` | invented for the headless tests; no such members exist in Minecraft |
| `GlStateManager.pushMatrix/enableBlend/...` | real methods with real SRG names; Aether reaches them by reflection, so the stub names never ship |
| `GuiScreen.drawScreen/initGui/...` | real methods; the *declarations* matter and the stubs made the names compile |

Two concrete consequences were found and fixed:

1. **The self-test classes were being packaged.** `AetherClickDeckSelfTest` and `AetherFontSelfTest`
   were compiled into the adapter output and copied into the jar, where they reference
   `Tessellator.setRecording`, `WorldRenderer$Batch` and `GlStateManager.lastColor` - members that
   exist only in the build's stubs. Any code path that loaded them would throw `NoSuchMethodError`.
   `forge189Jar` now excludes `**/*SelfTest*.class` (and the remapper, which is a build tool), so the
   jar contains 0 of them.
2. **The stub tree itself is a compile-time fiction that must be paid for at run time.** "Tests pass"
   and "production renders" are independent statements here, and the project's own tests cannot
   distinguish them - which is why §7 exists.

## 7. The fix: a real remapping step

`dev.aether.remap` implements the step Aether's build was missing, without adopting ForgeGradle's
whole architecture:

| Class | Role |
| --- | --- |
| `McpSrgMappings` | Reads an SRG mapping file (`PK:`/`CL:`/`FD:`/`MD:`), with owner-qualified lookups, ambiguity checks and the unmapped-reference report |
| `ClassFileRemapper` | Rewrites member references, declarations and class references in a class file |
| `RemapTool` | The build's entry point: remaps a tree of compiled classes, writes a report, and can fail the build |

Design points that are not incidental:

* **Renamed members get new constant-pool entries.** The same `CONSTANT_Utf8` backs a member reference
  and any string literal with the same text; rewriting it in place would turn
  `@Inject(method = "drawScreen")` - and every name in `Mc189Compat`'s reflective lookup lists - into
  something no refmap could resolve. Only `NameAndType` and declaration indices are repointed, so
  literals survive byte for byte. There is a test for this.
* **Declarations are renamed only in classes that are, or extend, game types.** A private helper that
  happens to share a name and descriptor with a Minecraft member must keep its name, because Aether's
  own calls to it are not game references and would not be renamed with it. There is a test for this
  too.
* **Ambiguity is refused, not guessed.** Two classes can declare the same name and descriptor with
  different runtime names; a lookup without an owner returns nothing, and the key is reported.
* **Fields are looked up by owner and name.** A field's descriptor is its own type and appears nowhere
  in a mapping table; using it as part of the key would silently miss every field the artifact touches.
* **Constructors and names already in runtime form need no entry**, so a missing `<init>` is not
  reported as a production hazard.
* **Everything else is copied verbatim.** Method bodies, stack maps, line numbers and nested
  attributes are untouched, so pool renumbering cannot disturb code the remapper does not interpret.

### Wiring

* `remapForge189` (Gradle) runs the tool after compilation into `build/remapped`, and
  `forge189Jar` takes its classes from there when an SRG mapping file is supplied
  (`-PaetherSrgMappings=<mcp-srg.srg>` or `AETHER_SRG_MAPPINGS`), with `-PaetherRequireRemap=true`
  turning any unmapped reference into a build failure. Without a mapping file the jar is still built,
  and the build prints a five-line warning saying exactly what that jar will do on a real client.
* `auditForge189` runs the same tool in report mode and writes
  `build/reports/unmapped-game-references.txt`, which lists every reference, mapped or not, with the
  class that makes it.
* `scripts/verify.sh` prints the two numbers that matter on every verification run - distinct
  Minecraft members needing a mapping, and call sites that would fail - so the count is visible and
  can only fall.
* The CI release job passes `AETHER_SRG_MAPPINGS` when the repository variable is set and turns
  `-PaetherRequireRemap` on with it; with the variable unset, existing behaviour is unchanged.

### Measured result

| Run | Development-form references remaining | Exit |
| --- | --- | --- |
| No mapping file (today's default) | 100 call sites, 48 distinct members | 0 with a warning, 2 with `--require-complete` |
| With a mapping covering those 48 members *and* the 9-signature dispatch surface | **0** | 0 |

The second run is the one that matters: 251 classes, 100 member references and 15 declarations
rewritten, and the tool then reports that *"the artifact references only names that exist on a
production runtime"*.

Two things in that run are not obvious and were each found the hard way:

* **The dispatch surface is invisible to a call-site report.** Minecraft calls `drawScreen`,
  `mouseClicked`, `keyTyped`, `handleMouseInput`, `mouseReleased`, `mouseClickMove`, `onGuiClosed`
  and `doesGuiPauseGame` - Aether never does - so no scan of Aether's bytecode can find them. They
  are 9 (name, descriptor) pairs that must come from the mapping file for the *declarations* to
  rename; the call sites alone cover only `initGui`. A mapping built from a call-site report alone
  leaves every screen's input and rendering hooks on development names.
* **Declarations whose target name the class already declares are skipped, and must be.** The
  hand-written SRG delegates mean 31 of the 46 would-be renames would collide with a method that
  already exists under the runtime name, producing two methods with one signature -
  `ClassFormatError: duplicate method name`, the class file rejected outright. The remapper compares
  each proposed declaration rename against the class's declared names and leaves the declaration
  alone when the runtime name is already there; the existing member *is* the override. This was
  caught by loading a remapped screen, not by reading one, and there is a regression test for it
  (`fixture/mod/PreNamed` in `McpSrgRemapperTest`).

The mechanism is complete; the only missing input is the mapping file itself, which ForgeGradle
generates as `build/mappings/mcp-srg.srg` and which is data, not code.

## 10. Exact root causes

1. **No remapping stage.** The jar ships development Minecraft names (100 call sites, 48 members),
   so on a production runtime the first hard-linked call site outside the reflective layer throws
   `NoSuchMethodError`. The screens themselves survive on their hand-written SRG delegates, which is
   why the failure presents as missing text and crashed HUD elements rather than a blank screen.
2. **The custom font fails once and is then abandoned, silently.**
   `AetherFontManager.rendererFor` wraps `GlyphPageFontRenderer.create` in `catch (Throwable)` and
   latches `failed`. In production the first call into the unremapped glyph code is
   `Tessellator.getInstance()` - `NoSuchMethodError` - which the latch swallows, logs once, and
   answers `null` for ever after. Every screen then falls back to Minecraft's font. This is the
   direct mechanism behind "the custom font never renders": not a texture problem, not a glyph
   problem, one swallowed linkage error on the first frame. (The latch exists for a good reason -
   retrying a failed build would re-rasterise and leak a texture every frame - but it must not
   classify `Error` as "environment lacks a font".)
3. **The Mixin layer cannot run or resolve**: no embedded runtime, no tweaker, no refmap, and the
   config points at a refmap file that is not in the jar. Five features are absent on a real client.
4. **The self-test classes were shipped** while referencing members that exist only in the build's
   stubs - a latent `NoSuchMethodError` in the artifact.
5. **The stubs let the build stand in for a runtime it never had**, which is why 27 test suites and
   2,238 font checks could pass while the artifact could not draw. "Tests pass" was never evidence
   about production, and the fix is not better tests but a step that operates on the artifact.

## 11. What this changes about the earlier findings

The previous audit's font work (texture-id resolution, the `Mc189Compat.drawString` dispatch, colour
measurement, colour state on the vertex, the glyph pipeline move) is all still correct and still
needed - but it addresses *how* text is drawn, not whether the names the drawing code calls exist.
With the artifact unremapped, none of it can even run: the font manager's failure latch converts the
first `NoSuchMethodError` into a permanent, silent fallback to Minecraft's font.

One correction to that audit is owed: it attributed the missing text to the font renderer's texture
and colour paths. Those were real defects, but they were not the production mechanism. In a real
client the glyph code never got far enough to bind a texture - it died at its first `Tessellator`
call, inside a `catch (Throwable)` that was designed to survive a missing font, not a missing build
step. The same audit's own rule said it: a successful compilation is not proof that the runtime
renders. It is equally true that a passing headless self-test is not proof that the artifact links.

The immediate-mode removal in particular turns out to have a second benefit here: the glyph and
decoration quads are now emitted through the same small set of `WorldRenderer` methods every other
primitive uses, which is 7 of the 48 members needing mapping instead of a wider spread.

## 12. Remaining issues

* **No Forge runtime was available in this environment.** No mixin was applied, no frame was
  rendered, no screen was opened. Every claim above is about the artifact and its inputs; the in-game
  result is still unverified by observation, by construction. §13 lists what to check first when a
  client is available.
* **The SRG mapping file is not in the repository** and cannot be invented: it is generated from
  Mojang's mappings by ForgeGradle. Until it is supplied, the build produces a development jar and
  says so loudly, and `scripts/verify.sh` prints the 100/48 count.
* **The mixin question is unresolved by design.** Aether still ships five mixin classes with no
  runtime to load them. The honest options are to embed and bootstrap Mixin 0.7 (as Leaf does), or to
  reimplement those five behaviours on the event bus. Neither is a small change, and both are
  decisions about the project's architecture rather than bug fixes.
* **`@Shadow` fields would need owner-aware declaration remapping.** Field *references* are safe
  (owner-qualified), and fields *declared* by a mixin are renamed by name alone, which is ambiguous
  when two classes share a field name - `air` on `Blocks` and `Material` is exactly that case, and the
  tool reports it rather than guessing. Aether currently uses no `@Shadow` fields, so nothing is
  affected today.
* **The refmap is still only produced with an SRG file**, and its correctness on the obfuscation
  environment Mixin 1.8.9 uses (`searge` vs `notch`) cannot be checked without Mixin itself.

### First checks with a real client

1. Does the client reach the main menu without `NoSuchMethodError`? If the jar is remapped, yes; if
   not, the exception's member name tells you which reference is uncovered.
2. Does the main menu show text? If glyphs are missing but the background is there, read the
   `[Aether] Custom font ...` line: it prints the atlas size, the texture id, whether the id came
   from Minecraft or from Aether's own upload - and, since the fix in §10.2, whether the build failed
   with an `Error` rather than a font problem, which is a different failure with a different fix.
3. F9 in the Control Center opens the font diagnostic, which draws one magnified glyph, its atlas
   rect and the resolved names in one screen - enough to separate "no texture" from "no text draw".

## 13. Two hardening fixes that fell out of the audit

Both are one-line behavioural changes to existing safety nets, and both exist because the audit
showed what each one silently eats in production.

**`AetherFontManager` no longer latches on `Error`.** `catch (Throwable)` treated a missing font and
a missing build step as the same event: one log line, `failed = true`, permanent fallback. The latch
is right for font-shaped failures (`FontFormatException`, a headless `GraphicsEnvironment`, no
texture); it is wrong for `NoSuchMethodError`/`NoClassDefFoundError`, which mean the artifact does
not link and no amount of retrying or falling back makes it work - but the operator needs the real
cause in the log, once, with its name. The manager now latches only on `Exception`, and an `Error`
is rethrown after one explicit report. In production today that turns "text is silently vanilla" into
"the log names the linkage failure on the first frame".

**The remapper refuses to create duplicate declarations.** Covered in §7; listed here because it is
a hardening of the new tool rather than a fix to old code. A class that already declares a member
under its runtime name keeps that member untouched, and the tool's own output stays loadable -
proven by loading a remapped screen in-process.
